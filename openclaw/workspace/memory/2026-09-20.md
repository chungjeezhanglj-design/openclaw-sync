### E. **Apple 的 VF 包装哲学**（⭐ 关键洞察，可复用于任何「私有 API 包装」场景）

1. **永远不直接操作 VF 原始类型**——先定义自己的 protocol（`VirtualMachineManager` / `Interface` / `VZInstanceExtension`）
2. **`toVZ()` 转换函数**——把自家 `Configuration` 转 VF `VZVirtualMachineConfiguration`
3. **`VZInstanceExtension` protocol** — `configureVZ` / `didCreate` / `willStop` 三时间点钩子，**可扩展点**
4. **钳制 VF 硬限制**——`min(vmConfig.memoryInBytes, ProcessInfo.processInfo.physicalMemory)`、`min(vmConfig.cpus, ...)`——VF 不让超物理内存/cpu，**包装层自己处理**
5. **自己 dispatch queue**——`queue.sync { ... }` 包住所有 VF 调用，避免 VF 内部多线程问题
6. **`withCheckedThrowingContinuation` 包 VF 回调 API** —— 把 callback-style 转 async/await

### F. VF API 实际用法（Apple 用的，记下来）

```swift
// 启动配置（VZVirtualMachineInstance.toVZ 里的核心模式）
var config = VZVirtualMachineConfiguration()
config.cpuCount = ...
config.memorySize = ...  // 向上对齐到 MiB 边界 (bytes + mib - 1) & ~(mib - 1)
config.entropyDevices = [VZVirtioEntropyDeviceConfiguration()]   // 必须：crypto 熵源
config.socketDevices = [VZVirtioSocketDeviceConfiguration()]      // 必须：guest-host vsock
config.serialPorts = [try serialPort(destination: ...)]          // 永远装串口（Linux 内核 printk 靠它）
config.bootLoader = VZLinuxBootLoader(kernelURL:, commandLine:)   // Linux 启动
config.platform = VZGenericPlatformConfiguration()                 // ARM generic（非 macOS guest 用）
config.networkDevices = try interfaces.map { try $0.device() }    // VZInterface → VZVirtioNetworkDeviceConfiguration
config.directorySharingDevices.append(VZVirtioFileSystemDeviceConfiguration(...))  // virtiofs
try config.validate()  // 强制验证

// 启 VM
let vm = VZVirtualMachine(configuration: config, queue: self.queue)  // 自己持有 queue
try await vm.start()  // async 包装见 VZVirtualMachine+Helpers.swift
```

**VF 关键限制**（Apple 自己处理）：
- **嵌套虚拟化**：M3+ Apple Silicon + macOS 15+ 才支持（`VZGenericPlatformConfiguration.isNestedVirtualizationSupported`）
- **Rosetta**：仅 Apple Silicon，3 种 availability（`VZLinuxRosettaDirectoryShare.availability`）
- **必须 vsock + entropy**——不装 VM 启不起来
- **memorySize 必须 MiB 对齐**——向上取整公式 `(bytes + mib - 1) & ~(mib - 1)`

### G. ⚠️ **Exec session / 工作目录教训**（重大）

今晚 try-omarchy / apple-container / apple-containerization 三次 git clone，**反复撞同一个坑**：

**症状**：
- `cd ~` → `git clone ...` → 进程**执行到一半被打断**（exec timeout / session killed）
- 重试时：`error: could not lock config file .../config: No such file or directory` 或 `fatal: your current branch appears to be broken`
- **根因**：上一次 git 操作**还没写完 .git/HEAD 就被打断**，**残留 broken 状态** + **lock 文件没释放**

**修复模式**（这次摸出来）：
```bash
# 1. 验证是否真的 clone 完成（看 .git/HEAD 存不存在）
[ -f ~/repo/.git/HEAD ] && echo "✅ 完整" || echo "❌ broken"

# 2. broken 就彻底清掉
rm -rf ~/repo

# 3. 重新 clone —— 不要 cd + clone 两条分开，先 cd 后 clone 一气呵成
cd ~ && git clone --depth 1 <url> <dir>
```

**更深层教训**：
- `git clone` **不要放在长跑的 exec session 里**——`--depth 1`（浅 clone）也至少 30-60s，**Apple 大仓库可能 1-2 min**
- 每次 exec 完成后**主动** `ls -la ~/<dir>/.git/HEAD` 验证完整性，**不要假设成功**
- `cd ~` + 长时间 `git clone` 单独跑一个 exec session，**不要** 跟后续命令串在同一个 session
- 多次连续 git 操作要 `--sleep N`，避免 lock 冲突（这次没踩，但理论上可能）
