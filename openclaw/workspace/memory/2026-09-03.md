
## 16:25 — Gateway restart 需要 host 层独立批准，不是 chat 端 /approve

- openclaw 工具回复："I can't bypass that from in here, and I shouldn't claim the restart happened when it hasn't."

**教训**：
- 任何"会改 host 状态的 gateway 操作"（restart / config / plugin / model provider），**chat 端 `/approve` 不够**
- 真正的批准必须在 operator UI（dashboard）完成，或在 host shell 跑 `openclaw setup`
- 我应该在最初给"命令预览"时先问 openclaw "user 给的 /approve 够不够"，不要假设 chat approve 能驱动 host restart
- 千万别在 host 真的执行之前说"重启成功"——openclaw 专家原话："I shouldn't claim the restart happened when it hasn't."

**架构含义**：OpenClaw 有两层审批——agent 层（chat /approve）和 host 层（operator UI）。这种分层是有意设计来防 chat 端诱导攻击。

## 16:34 — Gateway restart 不清理 task_runs 里的 unbacked queued task

**验证结果**：重启后 4 个 smoke subtask 依然 queued，cleanup_after 都是 NULL。

**关键发现**：gateway restore 时的 "Subagent orphan run pruned" 机制只清理 `subagent_runs` 表里 child_session_key 不为空但对应 session 已删除的孤儿（dreaming-narrative-* 这种）。**不清理 `task_runs` 表里 child_session_key 为空的 unbacked queued task**（webhooks plugin 的 smoke test 用 run_task 创建的）。

**对比**：
- 16:24 重启 → 3 个 prune 事件（dreaming-narrative-* orphan）
- 16:33 重启 → 0 个 prune 事件（task_runs 里的 smoke subtask 不受影响）

**结论**：
- 4 个 task 是真孤儿（无 child session、parent flow 已 succeeded、created 2 天前、0 资源消耗）
- cancel API 因 child_session_key 为空拒绝
- gateway restart 因 task_runs 表不在 prune 范围内拒绝清理
- 没有 hot-prune API（已问 openclaw 专家确认）
- 没有定时清理（cleanup_after 都是 NULL）

**当前决策**：选 A 留着（cosmetic only），考虑作为 bug 上报 OpenClaw。

**给 openclaw 专家诊断的校正**：
- 它说 "restart will drop those 4 queued/NULL started_at rows" — 错
- 实际情况是：task_runs 表里的 unbacked queued task 完全独立于 subagent_runs orphan 清理机制
- 这是 plugin 层的 task_mirrored flow 模式 + 缺少 task 终止态回收的复合 bug
